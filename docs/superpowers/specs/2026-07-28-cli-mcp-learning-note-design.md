# CLI 工具自动 MCP 化与技能生成学习笔记设计

日期：2026-07-28

## 背景

本仓库用于浙大控制学院夏令营考核项目。当前初步选题判断倾向于题目 2：“CLI 工具的自动 MCP 化与技能生成”。在正式决策和代码实现之前，需要先完成一份中文技术学习笔记，帮助建立对相关领域的整体理解，并为后续方案设计提供依据。

本设计 spec 定义学习笔记的目标、读者、结构、资料范围和验收标准。它不包含实现计划，也不启动代码开发。

## 学习目标

学习笔记采用“方案准备”深度。读完后应能支撑以下判断：

- 题目 2 研究的问题是什么，为什么它和 agent 工具调用有关。
- MCP tools schema 解决了哪些问题，又有哪些信息它本身表达不充分。
- skill 文件为什么有价值，它与 schema 的职责边界是什么。
- 为什么 CLI 工具适合作为自动工具学习的研究对象。
- 从 CLI 文档生成 schema 和 skill 时，需要抽取哪些信息。
- 最小 agent 执行循环、沙箱隔离、自动评测和失败归因分别承担什么角色。
- 后续正式方案设计大致应拆成哪些模块。

## 读者定位

目标读者是准备完成该夏令营考核项目的学生。读者可能熟悉大语言模型和基础编程，但不默认熟悉 MCP、Claude Skills、tool use benchmark、沙箱评测或 CLI-to-MCP 工具链。

因此笔记应先建立概念地图，再逐步落到项目设计启发。避免一开始进入工程细节，也避免停留在泛泛科普。

## 写作路线

学习笔记采用“概念链路优先，项目启发收束”的结构：

```text
LLM Agent
  -> 工具调用
  -> CLI 工具
  -> MCP tools schema
  -> skill 文件
  -> 文档到 schema/skill 的生成
  -> 沙箱执行
  -> 自动评测
  -> 失败归因与反馈修正
  -> 本项目最小可行系统启发
```

前半部分回答“这些概念是什么、为什么出现”；后半部分回答“这些概念如何组成题目 2 的实验系统”。

## 正文结构

正式学习笔记建议包含以下章节。

### 1. 从 LLM Agent 说起：为什么 agent 需要工具

说明普通 LLM 与 agent 的区别。重点解释 agent 不是只输出文本，而是需要观察环境、选择动作、调用工具并根据结果继续决策。引出工具调用能力对真实任务的重要性。

### 2. 工具调用的基本模式：ReAct、function calling 与 tool use

介绍 ReAct 的“推理-行动-观察”循环，以及 function calling / tool use 将外部能力结构化暴露给模型的思想。重点不是复现论文细节，而是理解“模型为什么需要清晰的工具描述”。

### 3. CLI 工具为什么适合作为研究对象

解释 CLI 工具的特点：文档通常可获取，输入输出可文本化，执行结果容易记录，任务可在本地文件系统中构造，适合做自动判分。同时指出 CLI 工具也有参数复杂、子命令多、错误信息分散、危险命令需要限制等问题。

### 4. MCP tools schema：把工具调用变成结构化接口

解释 MCP tools schema 的职责：定义工具名、描述、输入 JSON Schema、结果形式等。重点说明 schema 解决“如何调用”的问题，使模型或宿主系统可以知道参数结构、必填项和类型约束。

同时指出 schema 的局限：它通常不充分表达任务场景、调用策略、参数组合经验、常见错误、危险边界和多工具协作方法。

### 5. Skill 文件：补足 schema 之外的使用经验

解释 skill 文件的作用：告诉 agent 什么时候使用某工具、典型工作流是什么、哪些参数组合常见、哪些误用需要避免、失败后如何调整。强调 skill 与 schema 的互补关系：

- schema 更像“机器可验证的接口签名”；
- skill 更像“给模型看的操作经验和策略说明”。

### 6. 从 CLI 文档生成 schema 和 skill：信息抽取的核心问题

说明从 `--help`、README、用户手册和示例中需要抽取的信息：

- 命令与子命令；
- 参数名称、类型、默认值、必填性；
- 参数之间的互斥或依赖关系；
- 输入输出路径；
- 常见示例；
- 错误信息和限制；
- 安全风险与禁用范围。

这一节需要引出生成 pipeline 的基本阶段：文档收集、结构化抽取、schema 生成、skill 生成、格式校验、人工或自动审查。

### 7. 沙箱执行：真实调用工具，同时控制风险

解释为什么评测不能只看生成内容是否“像真的”，而要让 agent 真实调用工具完成任务。说明沙箱需要限制文件系统范围、命令范围、运行时间、网络访问和任务结束后的环境清理。

这一节应服务于后续实现判断，而不是深入容器技术细节。

### 8. 自动评测：任务成功率、token 消耗、对照实验

解释题目要求中的核心评价方法：任务成功率和 token 消耗。说明任务必须有自动判定标准，例如检查输出文件、JSON 字段、文本内容、命令退出码或生成产物属性。

对照实验应至少比较：

- 生成的结构化接口 + skill；
- 原始文档直接输入模型。

必要时可解释为什么只做人类主观评价不够。

### 9. 失败归因与反馈修正

解释失败分析应沿链路逐层定位：

```text
原始文档
  -> 生成的 schema
  -> 生成的 skill
  -> 模型工具选择
  -> 工具参数
  -> 执行结果
  -> 判分结果
```

重点说明失败可能来自文档缺失、抽取错误、schema 类型错误、skill 没写出限制、模型误判、沙箱限制或判分器设计问题。最后引出反馈修正循环：将失败信息回传给生成 pipeline，尝试改进 schema 或 skill。

### 10. 对本项目的启发：最小可行系统应包含什么

将前面内容收束到后续项目设计。这里不写最终实现方案，但应明确未来设计大概率需要包含以下部分：

- CLI 候选工具选择标准；
- 原始文档采集方式；
- schema 与 skill 生成器；
- schema 合法性校验；
- 沙箱执行器；
- agent 执行循环；
- 任务集与自动判分器；
- 实验记录与结果表格；
- 失败案例分析模板。

## 资料范围

正式学习笔记应优先使用以下资料类型：

- 题目要求中的参考文献：MCP Specification、ReAct、Voyager、ToolLLM、Tool Learning survey。
- MCP 官方 tools 规范，重点是 tool 定义、inputSchema、tool call、tool result。
- Claude Skills 或类似 skill 机制的公开说明，用于理解“自然语言工具使用经验”的角色。
- CLI-to-MCP 相关开源项目，例如 any-cli-mcp-server，用于了解已有做法与局限。
- 少量工具学习、agent tool use、function calling 的背景材料。

资料使用原则：

- 以官方规范、论文和开源项目文档为主；
- 不做大而全综述；
- 每个资料只提取对本项目设计有帮助的观点；
- 需要保留链接，方便后续报告复用。

## 非目标

本学习笔记不做以下事情：

- 不敲定最终选题实现方案。
- 不选择最终 CLI 工具集合。
- 不设计完整代码架构。
- 不实现 MCP server、agent loop 或沙箱。
- 不展开题目 1 的 V 模型多智能体方案，只在必要时作为对照背景提及。
- 不写成论文式文献综述。

## 验收标准

学习笔记完成后，应满足以下标准：

- 中文表达清晰，适合第一次系统了解该方向的人阅读。
- 章节顺序能从概念链路自然过渡到项目设计启发。
- 每个关键概念都回答“是什么、解决什么问题、对本项目有什么意义”。
- 对 MCP schema 与 skill 的职责边界解释清楚。
- 对沙箱、自动评测、对照实验和失败归因的作用解释清楚。
- 结尾能支撑下一阶段正式题目 2 方案设计。
- 保留主要参考来源链接。

3. 用户审阅学习笔记。
